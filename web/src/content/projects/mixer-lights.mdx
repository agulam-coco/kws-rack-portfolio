## Picking a mixer

My first idea was kind of a hack. You play a tone into the mixer, read how loud it comes out the other side, and that tells you where the fader is. Louder tone, brighter light.

The problem is these boards only have one main output. So if I want more than one bulb, how do I tell them apart? I was thinking maybe I could overlay a bunch of tones and pick them apart after.

Turns out that's a real thing. You give each channel its own pitch, mix them all together, and then the Pi splits them back up and checks how loud each pitch is. Each pitch is one bulb. That's how it would have to work on the Mackie, since it's fully analog and has no USB at all.

But then I found out the R24 can just skip all that. It's not only a mixer, it's also a USB controller. When you plug it into a computer, every fader sends its own message over USB. So fader 1 is bulb 1, fader 2 is bulb 2, and so on. No tones, no splitting anything apart. And Linux already supports it, so it should show up on the Pi without any extra drivers.

So I'm going with the R24. It's mine, it was already sitting in my room, and it makes the whole thing way easier. The tone thing is still a cool idea though, I might come back to it.

## Making sure it's actually an R24

I hadn't used it in a while, so I wanted to make sure it was the board I thought it was and not the R16, which looks almost the same. Easy way to tell: the R24 has drum pads (the KICK, SNARE, HAT labels under the faders) and bank buttons that go up to 24 tracks. Mine has both, so it's an R24.

One thing I noticed: the cap on fader 7 is missing. Hopefully the fader still works.

## The power problem

I lost the power adapter for the R24 a while ago. It takes 5V, and the official one is the Zoom AD-14.

I found an 18V adapter lying around and thought maybe it'd work for one of the boards. Nope. It's DC, which is wrong for the Mackie (that one needs 18V AC), and 18V would fry the R24. So that went back in the box.

![The 18V DC adapter that didn't work for either board](/media/projects/mixer-lights/wrong-adapter.webp)

The good news is the R24 can run off just USB when it's being used as a controller, which is the only mode I need. I tested it and it works off my laptop.

The bad news is it doesn't power on when I plug it into the Pi.

## Figuring out why

I plugged it in and looked at the Pi's logs. It was full of this, over and over, hundreds of times:

```
usb usb3-port1: over-current change #268
usb usb1-port1: over-current change #268
usb usb2-port1: over-current change #327
```

Basically the Pi kept cutting power to the USB ports because the R24 was pulling too much, then trying again, then cutting it again. The Pi itself was fine though. `vcgencmd get_throttled` came back `0x0`, which means it wasn't running low on power.

The catch is my Pi runs off PoE through a HAT, not a normal USB-C charger. A Pi 5 only lets the USB ports pull a lot of power when it can tell it's on a big enough charger, and through a HAT it can't tell. So it plays it safe and keeps the ports pretty weak.

There's a setting to lift that limit, but it's only safe if the HAT can actually give that much power. Otherwise you just move the problem to the Pi.

## Checking the HAT

So I looked up my HAT. It's a 52Pi P33, which does PoE and holds an NVMe drive. It's rated for 5.1V at 4.5A.

![The 52Pi PoE+ HAT on my Pi, with the NVMe drive on top](/media/projects/mixer-lights/poe-hat.webp)

I did the math on everything it has to power:

- **Pi 5:** about 2.4A maxed out, more like 1A normally
- **NVMe SSD:** about 0.6A maxed out, around 0.2A normally
- **USB ports (with the limit lifted):** up to 1.6A, but the R24 only needs about 1A
- **Total:** about 4.6A if literally everything is maxed, about 2.2A normally

The worst case is only if everything is maxed out at the same time, which isn't really happening with just a mixer plugged in. Normally I'll be using about half of what the HAT can give.

The HAT only gets its full power if the switch does PoE+, not plain PoE. I checked, and mine does PoE+. So I'm good.

Which means I don't have to buy anything. No new adapter, no USB hub. Just one line in the Pi's config:

```
usb_max_current_enable=1
```

That goes at the bottom of `/boot/firmware/config.txt`, then a reboot.

## Making it something other people can use

Somewhere around here I realized this shouldn't just be a script that only works in my room. A lot of people have an old mixer or MIDI controller sitting around, and a lot of people have smart lights. So I want to turn it into an actual open source project. You clone it, plug in your board, point it at your lights, and run it.

Right now it only has to work with what I have, which is the Zoom R24, Govee bulbs, and Alexa playing music. But I want it built so someone else can add their own mixer or their own smart home stuff without having to rewrite everything.

The way I'm thinking about it, there are three pieces:

- **Boards:** whatever has the faders. My R24, but also other mixers and MIDI controllers.
- **Devices:** whatever the faders control. My Govee bulbs for now, and the room volume.
- **The map in the middle:** a simple config file that says "fader 1 is the desk lamp" or "master is brightness for everything."

If you want to add a new board, you just teach it how your board talks. If you want to add a new kind of light, you just teach it how your light listens. Everything else stays the same.

Before writing any code I'm planning out the whole repo first: how it's organized, how setup works, and how someone would add their own stuff.

I wrote all of it up in an architecture doc so I could read through the whole thing before committing to it. The short version: every board gets turned into the same simple events ("fader 3 is at 62%"), a config file says what each control does, and plugins handle talking to the actual lights or speakers. Setup should be six commands: install, find the board, find the lights, move each fader to map it, run it, and make it start on boot.

The first version is just lights. Sound comes after that, then support for other people's stuff through Home Assistant. Next step is picking a name and actually starting it.

## Naming it

Naming took longer than I thought. I wanted something weird enough that nobody else would have thought of it. I went through a bunch of audio words like roomtone, bleed, sidechain, and ghostnote, but they were either already taken or too normal to search for. Sidechain is literally a crypto thing.

I ended up on **decibulb**. Decibel plus bulb. It's a little goofy, it says what it does, and when I searched it there was nothing out there with that name. It's free on PyPI and npm too, which matters if people are going to install it.

## Step 1: the skeleton

I'm building this one small step at a time and making sure each step actually works on the Pi before moving on.

The first step doesn't do anything useful on purpose. It's just the empty project with one command:

```
$ decibulb --version
decibulb 0.0.1
```

But that one command proves the whole setup works: the project installs, Python finds the code, and the `decibulb` command exists. Everything else gets built on top of that.

## Step 2: reading the mixer

Step 2 was getting decibulb to actually understand the R24.

First I had to install the MIDI libraries on the Pi. My Pi runs Python 3.13, and one of them (`python-rtmidi`) doesn't come prebuilt for that yet, so it has to compile on the Pi. That needed the ALSA headers installed first. After that, Python could see the board:

```
['Midi Through:Midi Through Port-0 14:0', 'R24:R24 MIDI 1 24:0']
```

The main idea of this step is that every board gets turned into the same kind of event. The R24 sends stuff like `pitchwheel channel=0 pitch=6731`, which means nothing to anyone. decibulb turns that into `fader.1 = 0.91`. A cheap Korg controller sends totally different numbers, but it would also come out as `fader.1 = something`. So the lights code never has to care what mixer you have.

The names come from a profile file for each board. It's just a list saying "channel 8 is the master fader" and "note 94 is play." If someone has a different board that speaks the same protocol, they can write their own profile without touching any code.

### Finding every button

Then I went through the whole board pressing everything and watching what came out. A few things surprised me:

- **I thought the F keys were backwards.** They weren't. I was pressing them right to left. Oops.
- **The jog wheel doesn't have a position.** It just spins forever, so it sends how far it moved instead. A 1 means one click clockwise, and a 65 means one click the other way.
- **The 8 buttons over the faders change depending on the mode.** In REC mode they send one set of numbers, in SOLO another, and in MUTE another. So it's really 24 buttons, not 8. I named them `rec.1`, `solo.1`, `mute.1`, and so on, so later each mode could do something different.
- **Pressing RHYTHM, then EFFECT, then USB made the jog wheel send a "moved zero clicks" message.** No idea why Zoom does that, but it's useless, so decibulb just ignores it.

### decibulb monitor

All of that became the first real command. `decibulb monitor` shows everything the board does, live:

```
Listening to Zoom R24 on R24:R24 MIDI 1 24:0. Press Ctrl+C to stop.
fader.1    ████████████░░░░░░░░ 0.62
master     ████████████████████ 1.00
play       pressed
play       released
jog        → +1
```

Watching the bar fill up as I push a fader is honestly really satisfying.

I also wrote 32 tests using the real numbers I got from the board. That way if I (or someone else) breaks something later, it gets caught right away, and nobody needs an R24 to run them.

## Step 3: talking to the bulbs

Now the other end: the lights.

My bulbs are Govee H6008s. I was hoping to control them over Wi-Fi, since Govee has a local network API for some of their lights. But there's no LAN Control setting for these in the app. My network does let devices see each other, so to be sure, I had the Pi send out Govee's "who's there?" message and waited. Nothing answered. These bulbs just don't support it.

Govee also has a cloud API, but it only allows about 10 requests per bulb per minute. A fader sweep sends like 20 updates a second, so that's nowhere close.

So I'm going with Bluetooth. The Pi has Bluetooth built in, and there's a library someone made for controlling Govee bulbs over Bluetooth. I scanned from the Pi and found my bulbs right away. Then I made each one blink one at a time so I could figure out which was which.

Funny thing: the Govee app said my Corner Lamp was offline, but it showed up over Bluetooth and blinked just fine. So it was only off Wi-Fi.

Bluetooth is actually a better fit anyway. It's completely local, it doesn't care about the campus network, and nothing goes through Govee's servers.

### The bulb plugin

Next I built the part of decibulb that actually talks to the bulbs.

It works like the board side, just flipped. Every board turns into the same events, and every device takes the same commands, like "set brightness to 0.62." So later, the code that hooks faders up to lights doesn't care if it's a Govee bulb over Bluetooth or some other light. If someone wants to add Philips Hue or whatever, they write one file and nothing else changes.

Before writing the Govee part, I read through the Bluetooth library's actual code to see how it works. Two things I found:

- **It drops the connection after 8 seconds of nothing happening.** That would mean every time I grabbed a fader after a break, there'd be a delay while it reconnected. So decibulb tells it to stay connected the whole time.
- **Govee bulbs can't go to 0% brightness.** The lowest is 1%. So the bottom of a fader is "as dim as it goes," and fully off is a separate command.

Then the first real test. decibulb connected to my desk lamp, dimmed it, brightened it, turned it red, then warm white. Seeing the actual lamp in my room do what my code told it to was a big moment.

I also ran a speed test, firing brightness changes at it as fast as possible:

```
speed test: 51 brightness steps, as fast as possible
10.1 updates per second
```

About 10 a second per bulb. A fader sends way more than that when you slide it, so decibulb can't just forward every single message or the bulb would fall behind and keep changing after you stopped moving. The plan is to only ever send the newest value. If you slide from 0 to 100 in half a second, the bulb doesn't need every step in between, it just needs to end up at 100.

### Finding the bulbs

Up to now I'd been finding my bulbs with little copy-pasted Python scripts. That's fine for me, but nobody cloning decibulb should have to do that. So I turned it into a command:

```
$ decibulb discover

MODEL   ADDRESS             NAME                    SIGNAL
H6008   ...                 ihoment_H6008_1F57      -52 dBm
H6008   ...                 ihoment_H6008_70C7      -40 dBm
H6008   ...                 ihoment_H6008_A93F      -51 dBm

Found 3 lights.
```

The bulb names are just random codes, so there's no way to tell which one is the desk lamp. Adding `--blink` makes each bulb flash one at a time, and you press Enter to go to the next. Same trick I used to figure out mine, just built in now.

The signal column is how strong each bulb's Bluetooth is. Closer to 0 is better. My desk lamp is right next to the rack so it's the strongest at -40, and the other two are around -52. All of them are way stronger than they need to be.

I also tested what happens if Bluetooth is off. The first version printed this mess:

```
decibulb: Bluetooth is unavailable: BLE scan failed: ('No powered Bluetooth adapters found. Turn on Bluetooth and try again.', <BleakBluetoothNotAvailableReason.POWERED_OFF: 3>)
```

Turns out the Bluetooth library wraps the real error inside its own error and pastes the whole thing into a string. I dug the original message back out, so now it just says:

```
decibulb: Bluetooth is unavailable: No powered Bluetooth adapters found. Turn on Bluetooth and try again.
```

Small thing, but error messages are the first thing people see when something goes wrong, so they should actually make sense.

### Wrapping up step 3

Last part of step 3 was tests for the bulb side. The tricky thing is nobody running the tests has my bulbs, and GitHub's servers definitely don't. So the tests swap out the Bluetooth library for a fake one that just writes down what it was told to do. Then they check that decibulb sent the right stuff: 62% when the fader is at 0.62, the color temperature clamped to what the bulb can actually do, the connection staying open, and so on.

One test even rebuilds the exact messy Bluetooth error my Pi spat out and checks that decibulb turns it into the clean version, word for word.

I also fixed a tiny thing I noticed: after the last bulb blinked, it still said "Press Enter for the next light..." even though there wasn't one.

57 tests now, all passing. decibulb can read every control on the mixer and control every bulb in my room. Next up is the actual point of all this: hooking the two together.

This is the part I actually wanted. Two new pieces:

Connecting corner_lamp...
Connecting wardrobe_lamp...

Then I moved fader 1 and the desk lamp followed it. That's the whole project working end to end, finally.

### Halfway didn't look like halfway

First thing I noticed: the bottom half of the fader felt pointless. At halfway the lamp already looked basically bright, and all the actual dimming happened in a tiny spot at the very bottom.

That's because of how eyes work. You notice small changes in dim light way more than in bright light, so 50% power doesn't look like half as bright. Real dimmers deal with this by using a curve instead of a straight line. decibulb squares the fader position now, so halfway on the fader is 25% power, which actually looks about halfway. Way better. If you want the old straight-line version there's a setting for it.

It's not perfectly smooth on really slow moves though. The bulbs only have 100 brightness levels, so if you creep the fader you can see it step. That's the bulb, nothing I can do about it.

## The lag

Everything worked, but the faders felt laggy. Move one fast and the lamp would keep sliding for a second or two after I stopped. Color temperature was the worst. One time I let go and it was still changing *seconds* later.

This turned into the longest part of the whole project so far.

### Trying to make Bluetooth faster

My first guess was Bluetooth. The bulb was taking about 100 ms per command, so I tried to make the Pi talk to it faster. There's a setting for how often the Pi and the bulb check in with each other, and I cranked it down. Took a reboot for it to actually apply, and even then it didn't help.

Then I tried skipping the step where decibulb waits for the bulb to say "got it" before sending the next thing. The bulb just disconnected. So it really couldn't take commands any faster.

### Faking the mixer

I wanted to catch the lag in a log, but I wasn't always at the board. So I wrote a little script that pretends to be the mixer. It "moves" the faders the same way I would, waits 5 minutes doing nothing, then moves them again, all through the real code and the real bulbs.

The log came back clean. Every command took about 45 ms. No dropped connections during the 5 minutes, no stuck commands. So whatever was causing the lag, it wasn't Bluetooth falling apart.

It did catch something else though. Two of my lamps were off the whole time, and decibulb had no idea, because it just assumed every lamp was on when it started. So it was happily sending brightness changes to lamps that couldn't show them.

### What it actually was

The bulb says "got it" in about 45 ms, but then it *fades* to the new value, and the fade takes longer than that. So if you send commands faster than it can fade, it starts lining them up and plays them one after another. That's the lag. decibulb was only sending the newest value like it was supposed to, but it was sending it too often, so the bulb built up its own backlog.

The weird part is that my Bluetooth change made it worse. It didn't help the bulb, but it made commands go out twice as fast as before, so the backlog built up faster.

The fix was to make decibulb wait between commands to each bulb, and keep grabbing the newest fader value while it waits. At 0.1 seconds, fast moves were perfect but slow moves still lagged, because a slow move keeps sending for longer and the line keeps growing. I tried a few numbers and 0.3 seconds was perfect.

So the bulbs can only really show about 3 changes a second. It still feels smooth because each one fades into the next.

## The board disappeared

A few days later I went to use it and decibulb couldn't find the R24 at all. `lsusb` didn't list it, and the Pi's log had this:

```
hwmon hwmon3: Undervoltage detected!
```

The Pi dipped in power for a couple seconds, right when the R24 was trying to start, and the R24 never finished turning on. The `usb_max_current_enable` line was still there. But this Pi is also running a bunch of Docker containers now, so there's less power left over for the R24 than when I first got it working. It was the power again.

The fix was switching the Pi off PoE and onto a full power cable. That gives the Pi more power to work with, so it has enough left over for the R24 too. The undervoltage warnings went away, and the R24 showed up again.

I wrote this up in the README too, with the options from best to worst: the board's own adapter, a powered USB hub, batteries, and last, the Pi's USB port. A setup that works one week can stop working the next just because you added something else to the Pi.

## Making it reliable

At this point decibulb worked, but only if everything was perfect when I started it. So I fixed the stuff that could go wrong.

- **It checks if each lamp is on.** Right after connecting, it asks every bulb whether it's on. If a lamp is off, moving its fader turns it on first, the master fader skips it, and the on/off button works on the first press.
- **It skips commands that don't change anything.** The bulbs round everything. Brightness only goes in whole percents, so 50.1% and 50.4% look exactly the same. Since every command now uses up 0.3 seconds, sending one that changes nothing just makes the next real change wait. decibulb works out what the bulb would actually show, and if that's what it's already showing, it doesn't send it.
- **It waits for the board.** Before, if the R24 was off when decibulb started, it just quit. And if I turned the R24 off while it was running, decibulb sat there forever, because a board that turns off doesn't send an error. It just goes quiet. Now it waits for the board to show up, notices when it disappears, and picks it back up when it comes back.
- **It keeps trying missing lamps.** If a lamp is off at the wall when decibulb starts, it tries again every 30 seconds. Once the lamp shows up, its fader just starts working. Not faster than 30 seconds, because searching for a lamp uses the same Bluetooth radio the other lamps are using.

All of that was needed for the last piece: running it on boot. decibulb is set up as a service now, so it starts when the Pi turns on and restarts itself if anything crashes. No SSH-ing in to start it.

### Lamps that drop out

A couple days later the board stopped doing anything. The log was full of this, over and over:

```
desk_lamp: connect failed: ... device not found: The device disappeared
```

The board was fine. Two of the lamps had dropped off Bluetooth while decibulb was running, and decibulb kept throwing every fader move at the dead connection. The Bluetooth library tries to reconnect on every command, but it never searches for the bulb again first, and once Linux forgets a bulb, nothing reconnects to it without a fresh search.

The startup retry already did that search, it just only ran for lamps that were missing when decibulb started. So now if a lamp fails twice in a row, decibulb gives up on that connection and hands the lamp to the same retry. It searches every 30 seconds until the lamp shows back up, and the lamp even keeps its fader level from before it dropped.
